# Google Drive同期：設計と検証

## 既存構成と追加方針

React 19・TypeScript・Vite・Dexie 4・Vite PWAを維持する。独自サーバー、クラウドDB、追加のランタイム依存は導入しない。既存データはIndexedDBの11ストアに保存されている。課題はレッスンの宿題・カテゴリ別内容、テーマの次の一歩、イベント内の作業として扱われ、独立した課題ストアはない。

アプリ起動時はRepositoryの `initialize` による移行後に履歴を初期化する。Reactの状態で画面遷移し、画面外でも同期サービスは継続する。終了時の通信は保証できないため依存しない。PWAとレスポンシブUIをそのまま利用する。既存のGoogleカレンダー機能はプロンプト生成で、Google認証処理は存在しなかった。

DB v4では既存スキーマを変更せず、次のストアを追加する。

| ストア | 役割 |
| --- | --- |
| syncEvents | 追記専用の変更履歴、送信済み／未送信、適用済み状態 |
| syncRevisions | 記録ごとの観測済み先端イベントID・項目名・競合状態 |
| syncConflicts | 現在表示している内容、双方の変更、競合項目 |
| syncMeta | 端末ID・端末名・アカウント紐付け・同期設定・状態 |
| syncMedia | 削除前も含めた添付原本のローカル保全 |
| syncOutbox | 確定した送信バッチ。応答喪失後も同じ内容で再送 |
| syncFiles | 検証・適用済みのDriveファイルID・ハッシュ・変更日時 |
| syncSnapshots | 端末内に保存する世代別の安全コピー |

既存 `.dancenote` は形式v1・データスキーマv3の互換性を維持する。同期内部テーブルや認証トークンは既存のエクスポートに含めない。既存バックアップのインポートは従来どおり全業務データの置き換えだが、同期履歴・紐付け・未送信履歴は維持し、インポートによる差分を新しいイベントに記録する。

## 履歴と因果関係

イベントは `eventId`、`deviceId`、`deviceName`、`recordType`、`recordId`、`operation`、`changes`、`baseRevision`、`before`、`after`、`createdAt`、`schemaVersion` を持つ。`changes` はトップレベル項目の値と存在有無の差分。省略された項目と空文字・nullを区別する。変更前後の行は競合確認と復元のために保持する。

`baseRevision` は単一の時計ではなく、その端末が観測した同じ記録の先端イベントID一覧。受信側は履歴グラフを検証し、祖先の変更を子孫の変更で置き換える項目別の複数値レジスタとして統合する。別記録と別項目は共存し、同一項目の異なる同時変更はどちらも残す。`createdAt` / `updatedAt` は表示用に整理するだけで、採用内容の判定には使わない。

配列は全体で一つの項目とする。カテゴリ配列、マイルストーン配列、作業配列の内部にさらにCRDTを導入するより、既存形式の維持と競合時の保全を優先した。配列内の別要素の同時編集は手動確認になるというトレードオフがある。競合解決は全先端を親にした `resolve` イベントで、競合しない項目を保った選択・手動調整を記録する。

DexieのDBCoreが書き込みトランザクションへ履歴ストアを追加し、業務データと履歴・リビジョンを同じ物理トランザクション内で確定する。単一トランザクション内の並列書き込みも順に記録する。リプレイはそのトランザクションだけ履歴の自動生成を停止し、リモート受信をローカルの新規変更として再送しない。履歴記録の失敗は元の変更もロールバックする。

イベントIDが同じ受信は二重適用せず、同じIDの異なる内容は拒否する。変更前値と観測リビジョンの整合性、欠けた親・循環、形式・型、一意制約、原本のハッシュを確認する。不正データは自動同期を停止する。同一日付・期間の別IDが既存の一意制約に当たる場合も、行を失わず競合として保持する。関連する記録が競合中の場合の添付削除も保留する。

開いている編集フォームの保存時にも、バックグラウンド同期で記録が変わったことを検出する。古いフォームが同期後の値や削除を上書きしないよう、再確認を案内する。これは端末内の楽観的ロックであり、端末間の採用判定に時計は使わない。

## Driveの保存形式と再送

Google Identity Servicesのブラウザ用トークン方式を使用する。トークンはメモリのみ。本人確認用のGoogle `sub` とメールを保存し、異なる `sub` の連携は受信・送信前に拒否する。Client Secret、リフレッシュトークン、トークンの永続保存は不要。初回統合はユーザーが内容を確認して開始し、その前に既存ローカルデータを保全する。

Driveは `drive.appdata` スコープの `appDataFolder` を使用する。通常のDrive一覧から見えず、同じアプリとアカウントからアクセスする。同一のOAuthクライアントIDを両端末で使用する。共有フォルダや公開リンクは作らない。

| ファイル名 | 内容 |
| --- | --- |
| dance-note-events-{batchId} | 最大100イベントのJSONバッチ、原本の参照 |
| dance-note-media-{SHA-256} | 画像・動画・サムネイルの原本 |
| dance-note-snapshot-{snapshotId} | 履歴・適用済みID・日時・形式・アカウントIDと検証済みバックアップ |

保存済みファイルは更新しない。同じ原本はハッシュの名前で再利用する。バッチはDrive送信前にIndexedDBへ確定し、成功確認後にイベントの送信状態とバッチ・受信済みファイル情報を同時更新する。通信応答が失われた場合は次回、保存済みの名前と内容を確認する。Driveが同名ファイルを重複作成した場合もイベントIDで二重適用を防ぐ。

送信バッチは親イベントが先に届く順序で組み立てる。検証済みのファイルはDriveの変更日時が同じなら再ダウンロードせず、変更日時が変わった場合は保存済みハッシュとの一致を確認する。不一致は書き換えとして停止する。

受信は全対象バッチと必要原本を検証した後に業務データ・履歴・受信済み情報を一括で確定する。ダウンロード中にアプリを閉じた場合は受信済みにしない。送信中に閉じた場合も未送信イベントと確定バッチが残る。独立端末の同時同期では各端末が別ファイルを新規作成するので、他端末の履歴を上書きしない。同一ブラウザの複数タブはWeb Locksがある場合に直列化する。

## スナップショットと復元

初回連携前、約24時間ごと、手動で作成する。記録とファイルを同一読取トランザクションで撮影し、ハッシュ計算と通信はトランザクションの外で行う。履歴JSONと既存 `.dancenote` の両方をSHA-256で検証する。既存形式の検証には型・重複・添付関連付け・ファイルサイズ・原本ハッシュの検証が含まれる。

複数世代をDriveと端末内に保管する。空の新端末は最新スナップショットから履歴を初期化して、それに含まれない新しいイベントを適用する。古いイベントファイルは削除しないため、全履歴での再構成も可能。

スナップショットは検証済みファイルの受信情報も含む。新端末ではこれを履歴と同じトランザクションで取り込み、既に収録された変更バッチの再ダウンロードを省く。端末内の安全コピーは `.dancenote-sync` としてダウンロード・確認し、同じ紐付けアカウントのローカル環境へオフライン復元できる。

復元では内容確認後に現在のスナップショットを先に作り、対象バックアップの記録を `resolve` イベントとして再保存する。バックアップにない現在の記録は削除しない。既存の一意制約で失敗した場合は全復元をロールバックする。連携解除後も安全コピーを端末内へ保持する。添付原本を自動削除せず、参照がなくなった原本はバックアップの現行添付から除外するだけにする。

## 容量・性能と現時点の制約

イベントをまとめるため、1,000イベントを一度に送る場合のイベントファイルは約10個。短い間隔で同期すると小さなバッチが増える。これに原本ファイルとスナップショットの世代数が加わる。ファイル数はイベント単位保存より減るが、Drive一覧は全件取得（1ページ最大1,000ファイル）する。受信済みバッチは再ダウンロードせず、新端末の初期化にはスナップショットを使用する。同一記録の統合はその記録の全履歴を読み、因果関係の探索が増えるので、長期・大量利用のベンチマークは今後必要。

履歴・原本・ローカル安全コピーを削除しないため容量は増え続ける。全端末の同期状況を追跡するGCプロトコル、履歴圧縮、自動世代削除は未実装。容量不足時には未送信データを保持してエラー表示する。大きな動画は原寸のまま保存し、SHA-256計算時に原本をメモリへ読み込む。JSONバッチ・履歴JSONは32 MiB、Driveファイルの送受信は512 MiBまで。multipartアップロードを使い、再開可能アップロードは未実装。

閉じたPWAでの同期、常時リアルタイム同期、無操作のトークン再取得は行わない。再起動・期限切れではユーザーの再連携を案内する。手動競合調整はJSONエディター。配列内の要素単位の自動統合、別アカウントへの同一ローカル環境の切り替え、巨大データの性能検証は未対応。

## 検証

`src/sync/sync.test.ts` は独立した端末相当のIndexedDBと仮想Driveで、双方向同期、オフライン編集、別記録の同時編集、同一項目／削除対編集の競合、重複適用防止、不正履歴の原子的な拒否、応答喪失後の再送、再オープン後の履歴保持、同時同期、添付原本転送、スナップショット保全・復元、アカウント混在防止、v3の無損失移行を確認する。

Google認証とDriveのHTTPアダプター、自動同期の待ち時間・定期実行・期限切れ・停止もモックで確認する。2026-10-11時点で既存機能を含む45ファイル・265テスト、TypeScriptの型チェック、通常／GitHub Pages向けビルドが成功。本番ビルドにはメインチャンク500 kB超過の警告があり、長期的な分割改善余地がある。利用可能なブラウザ自動化環境がなく、実画面の操作・表示確認は未実施。

Google Cloudのプロジェクト作成・OAuth許可は利用者が行う。実Googleアカウントでの疎通、実機のスマートフォンとPC、インストール済みPWAでのポップアップ・オフライン動作、Googleの実レート制限は、設定後の確認事項。
